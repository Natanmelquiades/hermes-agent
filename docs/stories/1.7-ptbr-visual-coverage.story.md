# Story 1.7 — Cobertura visual e migração de strings de interface pt-BR

## User Story

Como usuário do Hermes Desktop no Windows,
quero que as telas e controles visíveis também usem Português (Brasil),
para que a troca de idioma produza uma experiência coerentemente traduzida, e não apenas um catálogo estruturalmente completo.

## Contexto da story

Esta é uma continuação brownfield do locale `pt-br` já integrado ao mecanismo existente de i18n. A branch de trabalho parte da `origin/main` atual (`c47f0b4590`) e integra o checkpoint local `f71932021b` sem modificar a branch de checkpoint publicada no fork.

O Desktop é um renderer React/TypeScript/Vite dentro de um shell Electron. O contrato existente está em `apps/desktop/src/i18n/`, com `I18nProvider`, `TRANSLATIONS`, `useI18n()`/runtime translator e fallback para inglês. A auditoria inicial encontrou textos de interface ainda hardcoded em componentes como `components/ui/zoomable.tsx`, `app/settings/billing/index.tsx`, `app/settings/custom-endpoints-settings.tsx`, `app/settings/model-settings.tsx`, `app/settings/memory/provider-config-panel.tsx`, `app/pet-overlay/pet-overlay-app.tsx` e áreas do chat/sidebar.

Não há um diretório versionado `docs/architecture/` com documentação arquitetural específica neste checkout; a implementação deve seguir o contrato efetivamente usado pelo código existente e os padrões de `apps/desktop/src/i18n/`.

## Acceptance Criteria

1. A matriz `docs/qa/ptbr-visual-coverage-matrix.md` lista as superfícies visíveis prioritárias, seus componentes de origem, classificação de risco e evidência esperada.
2. Cada superfície P0/P1 é auditada em English e Português (Brasil), com o resultado registrado como traduzido, parcialmente traduzido, pendente ou não traduzível por ser conteúdo técnico/dinâmico.
3. Strings de interface hardcoded identificadas como traduzíveis são migradas para o mecanismo existente de i18n; nenhum mecanismo paralelo, dependência nova ou tradução textual global é criado.
4. Labels de acessibilidade, `aria-label`, títulos, placeholders, estados de carregamento/erro e mensagens vazias visíveis também são avaliados.
5. Comandos, IDs, URLs, protocolos, nomes de providers/modelos, nomes de ferramentas, nomes de skills/MCPs, logs, tracebacks e conteúdo produzido pelo modelo permanecem intactos quando forem dados operacionais ou conteúdo dinâmico.
6. A auditoria estrutural continua retornando `missing=0`, e os testes de aliases, runtime, fallback, persistência e seletor continuam passando.
7. A troca de idioma é validada visualmente no Electron/Windows nas superfícies P0, sem truncamento impeditivo, quebra de layout ou regressão ao retornar para outro locale.
8. Typecheck, lint, testes direcionados e build passam sem erro novo introduzido pela story.
9. As falhas gerais preexistentes de Windows/MSYS ficam documentadas separadamente e não são mascaradas como sucesso da tradução.
10. A story não cria PR nem faz merge no repositório oficial; checkpoints podem ser publicados somente no fork pessoal autorizado.

## Riscos e mitigação

- **Risco:** mover uma string operacional para o catálogo pode alterar comandos ou identificadores.
  **Mitigação:** classificar cada candidato antes da migração e testar interpoladores literalmente.
- **Risco:** textos maiores podem causar truncamento no Windows.
  **Mitigação:** validar fluxos P0 em janela real e registrar screenshots/logs sem dados sensíveis.
- **Risco:** fallback em inglês pode esconder uma tela não migrada.
  **Mitigação:** manter a matriz visual separada da auditoria estrutural e testar cada superfície.
- **Rollback:** reverter o commit da story ou retornar à tag `checkpoint/desktop-ptbr-f71932021b`; a branch `feat/desktop-pt-br` permanece congelada.
